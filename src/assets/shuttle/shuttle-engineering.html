Why single process?
Campus deployment is a single VPS. Keeping MQTT, Socket.IO, REST, and DB in one process avoids inter-process communication. If driver count grows significantly, the MQTT tracker can be extracted to a separate worker with shared Redis pub/sub.

JavaScriptmqtt-tracker.js — throttled broadcast
// Cache invalidated on every MQTT message — re-serialised max once per 500ms
const getMQTTDevicesData = () => {
  const now = Date.now();
  if (cachedData && now - cachedAt < CACHE_TTL_MS) return cachedData;
  cachedData = Array.from(mqttDevices.values());
  cachedAt = now;
  return cachedData;
};

// 1 broadcast/sec max — Traccar can fire multiple messages/sec per device
const broadcastMQTTDevices = () => {
  if (!socketIoInstance) return;
  const now = Date.now();
  if (now - lastBroadcast < BROADCAST_THROTTLE_MS) return; // throttled
  lastBroadcast = now;
  const devices = getMQTTDevicesData();
  if (devices.length) io.emit('mqtt-device-locations', devices);
};
JavaScriptmqtt-tracker.js — stale device cleanup
// Runs every 60s — prunes devices silent for more than 5 minutes
const cleanupStaleDevices = () => {
  const now = Date.now();
  for (const [id, device] of mqttDevices.entries()) {
    const lastSeen = new Date(device.position.serverTime).getTime();
    if (now - lastSeen > STALE_DEVICE_TTL_MS) {
      mqttDevices.delete(id); // bus is parked or tracker off
    }
  }
  invalidateMQTTDevicesCache();
};

Why Traccar over DIY MQTT broker?
Traccar is a battle-tested open-source GPS tracking platform. The physical GPS devices are pre-configured to send to the Traccar server, which re-publishes over MQTT. This means the backend never needs to manage GPS device protocols directly — Traccar normalises every vendor's proprietary format into the standard { position, device } envelope.
Coordinate Validation Guard
Messages with lat === 0 && lng === 0 are explicitly rejected — this is a common GPS cold-start artifact where the device hasn't acquired a fix yet. Storing zero-coordinates would snap buses to the Gulf of Guinea on the client map.

REST for metadata, Socket.IO for coordinates
Driver metadata (name, route, busID) changes infrequently — polling REST every 30s is appropriate. Position data changes every 2s — Socket.IO push eliminates the 30s latency that polling would introduce for location updates.

JavaScriptmqtt-tracker.js — buildDeviceDriverMapping()
// Called once on server boot — builds the fast lookup map
export const buildDeviceDriverMapping = async () => {
  const drivers = await DriverModel
    .find({ deviceId: { $exists: true, $ne: null } })
    .select('deviceId driverID'); // minimal projection

  deviceToDriverMap.clear();
  for (const driver of drivers) {
    deviceToDriverMap.set(String(driver.deviceId), driver.driverID);
  }
  // Map: "861694061234567" → "DRV-001"
  // O(1) lookup on every MQTT message — no DB round-trip per position update
};
sparse: true on deviceId
The sparse index allows multiple drivers to have null deviceId while still enforcing uniqueness for drivers who do have a device assigned. Without sparse, only one driver could have a null deviceId.
